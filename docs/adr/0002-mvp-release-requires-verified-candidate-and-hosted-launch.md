# The MVP is released by one human release act, after both the candidate and the hosted launch pass

The MVP implementation spec (#23) excludes provisioning and rollout of the hosted service. Yet the official desktop app preselects the hosted service as its server, and the official update channel shares its host, so a verified application whose default server can't be reached hasn't been released. We therefore define the MVP as **released** at the **release act**: the irreversible human step in which the live manifest first names 0.1.0 and the public download (GitHub Release `v0.1.0`) exists. The release act is allowed only after two independent gates pass: the **release candidate gate** (#66's audit of one identified desktop installer and server commit, with #59, #62, #63, #64 and #65 closed) and the **hosted launch gate**, which a separate hosted-launch spec owns rather than #23.

## Consequences

- The hosted launch gate requires the hosted service to run exactly the candidate's server commit behind trusted TLS, with production email delivery and Google/GitHub sign-in verified end to end, encrypted off-server backups and the independent deletion ledger in operation, a pre-release restore rehearsal on the hosted configuration, update metadata served statically with the live manifest answering 204, and the external availability probe with alert delivery running from a separate host. The hosted-launch grilling of 2026-11-10 added two items: authenticated ingress that attributes client addresses, and the operator's legal pages (Impressum, privacy policy, terms) and processor agreements.
- "0.1.0" here means the first released MVP version. Under ADR-0001's amendment, a failed candidate uses up its version.
- "Exactly the candidate's server commit" is strict: every new release candidate, even one with only desktop changes, is redeployed to the hosted service before the release act. We don't prove server equivalence between commits.
- Hosted availability (99.5% per month, measured externally) is an operating objective, not a release blocker, consistent with #23's list of release blockers. Before the release act, the probe must show a **burn-in**: availability of at least 99.5% over 7 × 1440 consecutive UTC minutes, with missing samples counted as unavailable. The burn-in starts once the hosted service runs the full stack (ledgers, backups, canary) on any default-branch commit. It ends no more than 24 hours before the release act, with the final candidate's server running for at least its last 24 hours. Redeploying a new candidate is maintenance, so it counts against availability but doesn't restart the window, and the burn-in can run alongside candidate validation. Monthly reports begin with the first full UTC month after release, and a missed month triggers an incident review, never a withdrawal of the release.
- Until the release act, the hosted service runs in `allowlist` registration mode (operator, canary, testers). Opening public registration is part of the release act, so the desktop release and the hosted service become public at the same moment.
- The hosted-launch spec also owns ADR-0001's rehearsal infrastructure (tester allowlist and protected rehearsal artifact route) and the release-act runbook, because both are operator work on the same proxy and host. Application changes, such as ADR-0003's certificate trust, stay in #23.
- #66 stays an audit of the application candidate and doesn't wait for the hosted launch gate. For hosted availability (story 84), its record points to the hosted launch gate, whose evidence completes on its own schedule. The only place that needs both gates passed is the release act's go/no-go record on #23.
- The release act has an order. Publishing the draft release makes the download public. The live manifest is then published asynchronously, and public registration opens only after the manifest names the version and the published hashes match. If manifest publication fails, the release is fixed forward and never unpublished. The release act is complete only once all three outcomes hold.
- A self-hosted server is versioned by the annotated tag `v0.1.0` and built from source with the repository's Compose file. No registry images are published for the MVP. The GitHub Release is the official download page and attaches the same verified installer, signature and signing evidence as the official update channel, with matching hashes.
- #23 closes only once the release act is recorded.

## Considered options

- **Treating the hosted launch as separate work entirely**: rejected, because the shipped desktop would preselect a server that doesn't work.
- **Folding hosted provisioning into #23, #66 or #111**: rejected, because #23 deliberately keeps the application operator-neutral, and provisioning work is mostly human operator tasks with their own evidence.
- **A full month of measured availability before release**: rejected, because it adds at least 30 days to the critical path for an objective #23 doesn't treat as a release blocker.

## Amendment 2026-11-11: no deletion ledger in the hosted launch gate

[ADR-0005](0005-account-deletion-is-a-hard-delete-in-the-application-database.md) replaced the independent deletion ledgers with a hard delete and a tombstone in the application database. In the hosted launch gate, "the independent deletion ledger in operation" becomes **the deletion log shipped and kept off the server, with the re-delete step rehearsed**: each deletion's line is appended to a monthly file in the Storage Box's deletion log directory before the deletion commits, kept until 31 days after its month ends, and the pre-release restore rehearsal re-applies it. The burn-in's "full stack" no longer includes ledgers: it is the hosted stack with backups and the canary.
