# Account email changes

Issue [#27](https://github.com/Umami-Creative-GmbH/pr0/issues/27) adds browser settings and public REST operations for explicit reauthentication and verified email replacement. Run the ordinary account migration command before starting this release; readiness requires schema version 6. No new secrets or services are required.

The current password can establish freshness. Accounts with no password use a code sent to their current verified email. Both paths grant a server-owned ten-minute proof for the same instance, account, browser session, and email version. Sign-in, session renewal, OAuth callbacks, generic OTP, and desktop approval do not grant this proof. A persisted device session remains a device session even when its token is supplied through a signed browser cookie.

Each email code has eight cryptographically random decimal digits, expires after five minutes, and permits three wrong attempts. Codes are stored as keyed digests; the durable mail queue encrypts their delivery payload. Resend replaces the preceding challenge of that purpose in the same browser. Account and session locks serialize attempts, successful consumption, revocation, password changes, and email changes. Email/version checks reject stale settings submissions.

The replacement address must be verified while freshness is still valid. The address change and old-address notification job commit in one transaction. Queue capacity or admission failure leaves the old address active. The new address preserves the same account/library; collisions never merge accounts. Changing email invalidates all account freshness proofs, pending challenges, and outstanding password-recovery tokens. Existing sessions retain their identity.

Mail uses the existing destination and ingress throttles. The old-address notice is subject to the same admission controls and has at most five SMTP attempts, bounded by a 24-hour job lifetime. Settings distinguish queued delivery, SMTP acceptance, and terminal failure. SMTP acceptance does not prove inbox delivery. Failure remains visible after the seven-day delivery-log retention period and does not roll back a completed, verified email change. Operators can inspect aggregate mail outcomes with the existing `accounts mail-status` command and redacted worker logs. A later email change supplies the latest notification status in settings.

The published OpenAPI document describes `GET /api/v1/account`, `POST /api/v1/account/reauth/challenges`, `POST /api/v1/account/reauth/verify`, `POST /api/v1/account/email/challenges`, and `POST /api/v1/account/email/verify`. Unlisted Better Auth routes remain disabled. These operations require verified browser sessions and same-origin mutations; they do not add desktop commands or permissions.

Run `bun run --cwd apps/web test:email-change` for a fresh production build, disposable PostgreSQL/SMTP services, public HTTP security tests, SMTP outage verification, and account/recovery regressions. The fixture shares the provider responses and local ports from `tests/social.env`; do not run it alongside the social suite. No real email or provider accounts are used. Clock/provenance changes are fixture setup; behavioral assertions read public API responses.
