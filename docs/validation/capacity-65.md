# Capacity validation for issue #65

This work adds repeatable capacity workloads and fixes measured search/indexing overhead. It does **not** establish that #65's release budgets are met. The ticket remains open. The user authorized this Windows host for supporting evidence; it is not the required four-core, 8 GiB SSD benchmark machine.

## Environment and scope

[Host inventory](../evidence/issue-65-host.json) records Windows, CPU, RAM, SSDs and the Linux Docker VM. The desktop uses a release-profile native test executable with production Vite assets and real WebView2/typed native commands. Snapshot transport and account credentials are fixtures. The worker does not start production background synchronization loops, so its ten-minute process-tree sampling is **offline supporting evidence**, not the settled online/no-backlog gate. Other validation work ran concurrently on this host.

The service fixture runs production images on Linux x86-64. Web, PostgreSQL, mail, SMTP and both deletion ledgers share CPUs 0 and 1; memory limits total 3,776 MiB. Docker's backing disk and kernel are shared. No dedicated 64 GiB disk or physical two-vCPU/four-GiB machine is claimed. The fixture uses a private trusted-ingress secret and distinct synthetic source IPs only for account provisioning, preserving production sign-in throttles.

## Changes prompted by measurements

- Native short postings now collect bounded, transaction-local bitmaps before persistence instead of repeatedly expanding dense postings into trees. The cache retains at most 16,384 entries, below 21 MiB of bitmap payload, and is released before commit. Existing minimal sparse/run/bitmap encodings and transaction boundaries remain.
- Native query candidates use fixed-domain membership bitsets; unfiltered searches avoid decoding every tag array. A revision-bound organization-name cache and compact metadata/count projection remove repeated canonical-body scans from search and status paths. Mutation admission and recovery retain canonical reads. Full SQLite/FTS integrity checks remain enabled.
- Server bitmap updates modify a bit and compute cardinality/run counts without allocating and sorting thousands of entries. Public REST and native regressions verify complete dense postings after changes and restart.
- Large compact collection/tag pickers open through keyboard-accessible native disclosures. This removes 1,200 unopened choices from render/focus paths and bounds option scrolling. Every option and selected identity remains available. The native prompt footer scrolls rather than covering final actions.
- Opening the native editor fetches a fresh command snapshot. Copy updates local usage/revision; reusing an older detail snapshot caused a subsequent save refusal. Draft account/instance fences remain.
- Bun is pinned to 1.4.4 in deployment/tooling and CI. On the previous Linux 1.4.2 runtime, a reserved SQL transaction was terminated by the pool's idle timeout during long index preparation. An isolated transaction with a one-second idle timeout and a two-second asynchronous pause failed on Linux 1.4.2 and completed on Linux 1.4.4. The separate CPU-bound pause completed on both versions in the retained reproducer. [Raw runtime comparison](../evidence/issue-65-sql-lifetime.json) and `apps/web/tests/capacity-sql-lifetime.ts` retain that distinction. No database pool timeout or durability policy was weakened. The Docker digest is pinned for reproducibility. [Bun SQL transaction documentation](https://bun.com/docs/runtime/sql).

## Workload and evidence

The deterministic desktop corpus contains exactly 10,000 prompts and 104,857,600 logical UTF-8 bytes, including title, description, content, 200 collection names and 1,000 tag names. Every prompt has 20 tags; Unicode-heavy noisy bodies avoid tiny compressible placeholder content. Search samples include a one-character term, punctuation, common body content, all five fields, Greek/CJK, emoji, a near-limit multi-term query, and an absent query. The added `abcd` case has trigrams present in all bodies but exactly seven literal matches in the deterministic noise; it forces exact verification of the full candidate set. Typed pagination checks all 10,000 identities with no duplicates after persisted restart. Search timing starts at input dispatch and ends after result commitment plus two animation frames, including the production debounce.

The original launcher samples included Playwright actionability waits on an inactive surface. [Alternating trigger diagnosis](../evidence/issue-65-launcher-trigger.json) separated that overhead: subsequent Playwright clicks took about 2.96 seconds to dispatch, whereas direct DOM activation took 7–24 ms and reached native focus in another 1–6 ms. The revised collector records one warm-up separately, then twenty main-button DOM activations through native focus and an enabled focused search field. This measures the main-button entry point; physical global-shortcut timing remains unmeasured. Copy and save start at the final action and end at acknowledged dialog closure plus two animation frames. These are twenty-sample nearest-rank p95s. Cold start is one process launch, not a cold-start p95 distribution. Snapshot pages are 250 records, bounded by the public contract; early baseline pages used 100 records, so download comparisons are not isolated microbenchmarks.

The service seed asserts exactly 1,000 accounts, 10,737,418,240 aggregate logical UTF-8 bytes and 109,900 prompts. One account has the maximum library; the other 999 have 100 prompts each. All 1,000 search indexes are prepared before load. Twenty authenticated accounts receive fixed arrivals: ten requests/second for 1,800 seconds and thirty/second for 60 seconds, 80% searches and 20% durable usage mutations. Timed refusals, timeouts, late dispatch and exhausted client concurrency are retained rather than retried or counted as successful throughput. Accepted usage counts are verified exactly after a production-server restart.

The REST catch-up supplement delivers 1,000 creates containing 10 MiB of desired text with receipt checks. It does **not** measure 1,000 queued native edits or the required shaped network. Inspection of native upload code confirms one operation per upload cycle; the native catch-up release gate remains open. The service image was built before the final shared-picker UI changes; its web timing observations therefore describe that earlier UI asset build. The service REST/index changes are present. The web supplement uses CDP 50 ms/20 Mbps shaping and two pages of the same browser session; it is supporting web propagation evidence, not independent desktop-device synchronization.

## Follow-up startup and memory profiling

The user requested profiling and fixes on this same host. The short feedback loop is `bun run apps/web/tests/capacity-desktop-profile.ts <release-test-executable> <retained-library-directory> <output.json>`. It verifies real initial results and the seven-match adversarial query, then samples the native/WebView tree after thirty seconds hidden. This point sample does not replace the ten-minute workload.

[Native startup timing](../evidence/issue-65-native-startup-profile.json) isolates the dominant delay to the full content FTS integrity check: about 9.4 seconds of the roughly 9.7-second recovery path. Table checks, the other FTS fields and short postings account for the remainder. Moving the configured cache before validation did not materially help and was reverted. A separate [Bun SQLite compaction probe](../evidence/issue-65-fts-compaction-probe.json) on a disposable database copy measured 6.48 seconds before compaction and 6.44 seconds afterward; its absolute timings are not interchangeable with the Rust build. Compaction did not solve the delay. Full integrity checks remain unchanged. A faster startup path with equivalent corruption detection remains unresolved.

Reducing the single SQLite page cache from 64 to 16 MiB addresses a confirmed native allocation cost. With the same visibility hint and short workload, native private commit at thirty seconds hidden fell from 89,632,768 to 28,889,088 bytes. [The complete smaller-cache point sample](../evidence/issue-65-desktop-profile-small-cache.json) still totaled 338,386,944 bytes, above the 300 MiB process budget. A [control](../evidence/issue-65-desktop-profile-control.json) and [visibility-hint run](../evidence/issue-65-desktop-profile-memory-hint.json) did not demonstrate a material total-memory benefit from the hint alone. The hint requests low memory for hidden/minimized WebViews and restores normal mode when visible; it is best effort and preserves scripts. [Microsoft documents these semantics](https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/icorewebview2_19?view=webview2-1.0.4022.49).

The complete interaction profile revealed a second issue in measurement. A [detailed allocation summary](../evidence/issue-65-webview-allocation-summary.json) and [compressed raw Chromium trace](../evidence/issue-65-webview-allocation-trace.json.gz) retain about 216 MiB in the main renderer's buffer partition and 2,624 inspector network-resource records despite only about 13 MiB of live JavaScript heap. Allocator categories overlap and must not be summed. Inspector response retention is a hypothesis, not an established cause of the entire footprint. Disconnecting automation did not reduce the immediate private-commit sample; the remaining buffer ownership and lifetime are unresolved. The dump does rule out a comparably large live JavaScript heap at that observation. The first instrumented interval included explicit CDP heap reads and a non-forcing memory dump; it is profiling evidence, not an uninstrumented idle gate.

The first [instrumented full workload](../evidence/issue-65-desktop-instrumented.json) retained all nine twenty-sample searches, all 10,000 paginated identities and twenty Copy/Save journeys. Copy p95 was 88.9 ms, Save 163.5 ms and warm launcher 10.9 ms. Cold UI remained 11,868 ms; the adversarial search remained 364.1 ms p95. Its [instrumented process-tree interval](../evidence/issue-65-residency-instrumented.json) peaked at 800,391,168 private bytes over 601.1 seconds. The debugging and concurrent native regression runs limit the CPU observation; these results are not a residency pass.

The revised collector disconnects browser automation before settling and sampling while leaving the native application and both native-owned WebViews alive. A separate small-fixture check confirmed that the native process survives disconnection. [Playwright documents disconnection for an attached browser](https://playwright.dev/docs/api/class-browser#browser-close). The helper waits for both native surfaces to attach before handing them to tests, correcting a release-profile startup race. Clearing the search field uses the same DOM input-dispatch mechanism as the measured query, avoiding unrelated Playwright foreground-actionability delays outside the timing boundary. No forced GC, browser cache clearing or skipped application work is used for the corrected residency measurement. Subsequent inspection also found Playwright's default focus emulation on CDP connections. The helper now connects with noDefaults=true, preserving native focus, font and media settings; historical launcher timings collected with those overrides cannot certify actual Windows focus. [Playwright documents the overrides](https://playwright.dev/docs/api/class-browsertype#browser-type-connect-over-cdp).

The [full detached-automation workload](../evidence/issue-65-desktop-detached-automation.json) completed the same searches, 10,000-identity pagination and twenty Copy/Save journeys. Its [ten-minute interval](../evidence/issue-65-residency-detached-automation.json) peaked at 841,613,312 private bytes. Disconnecting the observer alone did not solve residency. This run predates the noDefaults correction, so its launcher focus observations remain provisional.

A separate paired control sends 100 identical, schema-validated public native search requests from an opt-in test script. It uses the same native app and visible UI, then hides the app for thirty seconds. The [unobserved control](../evidence/issue-65-observer-control-unobserved.json) has no remote debugging flag or connection; the [observed control](../evidence/issue-65-observer-control-observed.json) attaches Playwright with noDefaults=true before the queries. Hidden process-tree private commit was 337,014,784 and 401,211,392 bytes respectively. This pair supports an observer-overhead concern; it is one pair, not a stable estimate of debugger cost or evidence that instrumentation explains the entire footprint. Neither point sample certifies residency.

The subsequent [collection-navigation experiment](../evidence/issue-65-observer-control-navigation.json) reduced idle DOM elements from 2,167 to 1,162 using the existing disclosure. However, hidden total private commit rose to 495,513,600 bytes, with GPU-process private commit rising from 86,863,872 to 282,468,352 bytes. That large variation also limits the observer comparison. No material total-memory improvement was established, so the UI experiment was reverted. Its [candidate patch](../evidence/issue-65-navigation-probe.patch) is retained for reproducibility. A real native keyboard/selection regression passed on the candidate before reverting it.

The observer script uses a bounded, opt-in reporting command compiled only into the native WebView test harness. It adds no production command or capability. Authorization still restricts the reporting handler to the main window. Initial [probe bootstrap failures](../evidence/issue-65-observer-probe-bootstrap-failures.json) retain a missing test-context capability and a Zod initialization-before-CSP issue; these were corrected in the harness without weakening production CSP. The unobserved replay creates no CDP session and does not force garbage collection.

## Reproduction

Use Bun 1.4.4 and Rust 1.94.0. Commands run from the repository root. Docker Desktop with Linux containers and installed Chrome/WebView2 are required for the respective harnesses.

```powershell
bun install --frozen-lockfile
$env:VITE_API_BASE_URL='https://localhost.invalid' # test assets; use the deployment API origin for a shipped build
bun run --cwd apps/desktop build
cargo test --manifest-path apps/desktop/src-tauri/Cargo.toml --release --features search-webview-test --lib --no-run
# Embed apps/web/tests/webview.manifest in the generated test executable with Windows SDK mt.exe.
$env:PR0_CAPACITY_RESIDENCY='true'
$env:PR0_CAPACITY_PROFILE='true'
bun test apps/web/tests/capacity-desktop.test.ts
# Replay the short observer control on a retained maximum library (no ten-minute certification):
bun run apps/web/tests/capacity-desktop-observer-probe.ts <release-test-executable> <retained-library-directory> unobserved <output.json>
bun run apps/web/tests/capacity-desktop-observer-probe.ts <release-test-executable> <retained-library-directory> observed <output.json>

docker build --target runtime -t pr0-capacity-65 .
docker build --target migration-runtime -t pr0-capacity-tools-65 .
bun apps/web/tests/capacity-service-runner.ts --web --keep-on-failure
# If a retained full run needs independent post-load verification:
bun apps/web/tests/capacity-post-load.ts docs/evidence/issue-65-service-prepared-web-failure.json
```

The desktop harness uses a fresh temporary library unless PR0_CAPACITY_REUSE_DIRECTORY names a retained fixture; reused runs explicitly omit initial-download timing. PR0_CAPACITY_KEEP=true retains local evidence after failure. The service runner removes its disposable Docker project normally; --keep-on-failure retains it and prints its exact location. --smoke shortens intervals and cannot pass the full-load flag. Capacity tests are explicit opt-in integration workloads, not part of the fast workspace suite. `--resume <report.json>` reuses an already prepared retained fixture whose primary counts still match the original seed; this skips reseeding and preserves the original seed evidence. `--smoke` shortens only timed intervals; all 1,000 indexes are still required. A failing web supplement is retained separately and no longer prevents the independent load phase from running.

## Remaining acceptance gates

Required-machine measurements, installed desktop cold-start p95, online initial download/indexing, actual native queued-edit reconciliation, independent cross-device visibility, settled ten-minute ordinary-sync/no-backlog residency, and disk-threshold behavior at 70%/80% are still required. Full service storage must include primary indexes, postings, WAL, scratch and both deletion ledgers under the provisional 64 GiB footprint. A load-only passed flag describes the collected subset; it does not close #65.

## Validation

The workspace suite passed 145 tests (84 contract, 49 client, seven web and five UI), and typechecking passed. The production-build REST/browser regression run passed 35 tests across dense short postings, all-field Unicode search, filters, organization management and retained editor behavior. The initial browser failures were a readiness race in the new picker helper and a pre-existing row selector that omitted the preview from its accessible name; both are corrected. The full release-profile native suite passed 169 tests, including migrations, interrupted writes, recovery, upload replay, Unicode matching and dense postings. The final capacity-run results and remaining failures are recorded above. Formatting, Rust formatting, frozen-lockfile installation and final typechecking pass. No acceptance criterion has been weakened or waived.

Follow-up validation passed the 145-test workspace suite, the 170-test release native suite with the WebView feature, and all fourteen real native UI tests across launcher, residency and startup. An initial UI run overlapped the benchmark's global shortcut registration and hit three failures, including a WebView attachment race. After the helper fix and with the benchmark process stopped, all fourteen passed. Typechecking and formatting pass.
