# Rust SQLite and Windows credential validation

Research for [issue 14](https://github.com/Umami-Creative-GmbH/pr0/issues/14), supporting [architecture decision 10](https://github.com/Umami-Creative-GmbH/pr0/issues/10). Investigated 2026-09-19. This is a candidate selection and isolated evidence record, not a production implementation or a completed release acceptance test.

## Result

Recommend `rusqlite = 0.40.2` with its `bundled` feature for Rust-owned SQLite transactions, and Microsoft `windows-sys = 0.61.2` bindings to Windows Credential Manager (`CredWriteW`, `CredReadW`, `CredDeleteW`, `CredFree`) for device credentials. The checked-in harness locks all dependencies; its actual bundled SQLite reports **3.53.2**. Both candidates compiled and ran on this Windows host with Rust 1.94.0, target `x86_64-pc-windows-msvc`.

The generated-data harness passed atomic save, forced process termination, reopen, migration rollback and interrupted migration checks. Generated Windows credentials survived a new process and supported isolated names, replacement and deletion without an application unlock prompt. This is evidence for the primitives. Normal Windows restart/logon, a physically full volume, installed upgrades, and the production Tauri command/HTTP boundary remain untested. The user accepted these native candidates and assigned the remaining implementation checks as mandatory release tests in [architecture round 3](https://github.com/Umami-Creative-GmbH/pr0/issues/10#issuecomment-5742931074). Primitive-selection research is complete; issue 10 owns the release gates below. This does not certify a production integration.

The accepted foundation is ordinary SQLite under Windows user-directory permissions, with credentials separately Windows-protected. Account and offline rules are authoritative in [account resolution](https://github.com/Umami-Creative-GmbH/pr0/issues/5#issuecomment-5742474484) and [offline resolution](https://github.com/Umami-Creative-GmbH/pr0/issues/6#issuecomment-5742539348). No new product policy is selected here.

## Rust storage boundary

Use one Rust storage worker per active library, owning the writable connection and serializing bounded commands from both library and launcher windows. Run blocking database work on its dedicated thread, not the WebView/UI thread. All saved changes, including synchronization application, go through that owner. Emit invalidation events only after commit; both windows read authoritative committed data. An event does not itself save anything. An expected local revision on edits can prevent a stale window from silently replacing newer saved work; the final revision contract belongs to issue 10.

A save command must start `transaction_with_behavior(TransactionBehavior::Immediate)`, validate the active account/instance and expected state, update the prompt and related search/index state, insert its pending synchronization operation with stable identity and required baseline, and commit the **same transaction**. Return success only after `commit()` succeeds. A retry with the same local operation identity must detect its previous completion. Do not hold the transaction across HTTP, clipboard, UI or other user interaction. These are proposed implementation boundaries, not claims that the harness implements the domain schema.

The pinned rusqlite source retains a connection reference inside `Transaction`; `Immediate` executes `BEGIN IMMEDIATE` on it. `commit` executes `COMMIT`; default drop behavior rolls back an active transaction. Dropping ignores rollback errors, so production should handle explicit failure paths, check that the connection returned to autocommit, and retire/reopen a connection whose state is uncertain. Never acknowledge a failed commit. This source was inspected in the downloaded `rusqlite-0.40.2/src/transaction.rs`, lines 118–129, 187–229 and 243–247. [Transaction API](https://docs.rs/rusqlite/0.40.2/rusqlite/struct.Transaction.html), [source](https://docs.rs/rusqlite/latest/src/rusqlite/transaction.rs.html)

This avoids assuming connection affinity between separate guest SQL calls. SQLite permits one writer while other connections read committed snapshots; `BEGIN IMMEDIATE` can report busy before changing data. The harness proves these behaviors across two Rust connections, not actual Tauri windows. [SQLite transaction semantics](https://sqlite.org/lang_transaction.html)

## Connection settings, files and failure handling

Proposed startup contract:

- Resolve `app_local_data_dir` in Rust, keeping the bundle identifier stable. Use a separate directory/database per authenticated instance and account, using opaque stable identifiers rather than email or renderer-supplied paths. Store the instance identity and canonical API origin in the partition metadata and validate before upload. Tauri documents an application-specific local-data path; it does not itself prove the deployed directory's ACL. [Path API](https://v2.tauri.app/reference/javascript/api/namespacepath/#applocaldatadir)
- Create/verify a private user directory on a local supported filesystem. Include database, `-wal`, `-shm`, migration backups and recovery files in the same access policy. Ordinary SQLite is plaintext. A Windows DACL controls permitted access; a missing DACL permits full access. Inspect effective access in the packaged application's real directory instead of assuming any directory under an app name is private. This does not defend against administrators or code already executing as the same user. [Windows ACL model](https://learn.microsoft.com/en-us/windows/win32/secauthz/access-control-lists)
- Before accepting commands, set and verify `journal_mode=WAL`; configure every connection with `synchronous=FULL`, `foreign_keys=ON`, and an explicit bounded busy timeout. The harness uses 150 ms solely to make contention observable; production timeout/retry limits must fit the accepted responsiveness budget. WAL/FULL synchronizes each commit; NORMAL can lose a committed transaction after power loss. `foreign_keys` is connection-specific and must be set outside transactions. [SQLite PRAGMAs](https://sqlite.org/pragma.html)
- Keep write transactions and readers short. Retain WAL autocheckpointing initially, inspect WAL growth, and schedule passive checkpoints away from UI work. WAL is part of database state: never delete it to “repair” a database or copy only the main file while writes are active. Use SQLite's backup API for an online backup or a verified quiescent snapshot. [WAL operation](https://sqlite.org/wal.html), [backup API](https://sqlite.org/backup.html)

On `SQLITE_FULL`, I/O errors or failed commit, roll back if needed, report **Not saved**, and keep the editor draft. On bounded lock contention, retry the complete operation using its same identity or return an actionable busy result. On corruption, preserve evidence and pending data, stop writes, and require a recovery path; never silently replace the database with a fresh download. SQLite may roll back a statement or the entire transaction after storage errors, so code must inspect transaction state. Actual durability also depends on the OS and storage honoring sync requests. [Error semantics](https://sqlite.org/lang_transaction.html#response_to_errors_within_a_transaction), [storage caveats](https://sqlite.org/howtocorrupt.html)

## Migrations and restart

Recommendation: a Rust-owned ordered migration list, a persisted schema version, and startup compatibility checks before enabling writes or synchronization. Each migration changes schema/data and advances its version in one transaction. Reject an unknown newer schema without mutation; do not attempt an automatic destructive downgrade. For a transform needing substantial scratch space, preflight and make a verified backup; failed backup or insufficient space blocks migration while preserving the original. Recovery must preserve pending changes, stable operation identities and synchronization baselines, not just prompts.

The harness demonstrates rollback of an `ALTER TABLE` plus version update when a later SQL statement fails, successful reopen after commit, and forced child termination before/after a migration commit. The prior prompt and pending operation survive both cases. It does not validate a real application schema, migration chain, installer rollback or recovery UI. Release validation must start from every supported upgrade source with unsynchronized edits and verify downgrade refusal. Transaction semantics support the strategy; tests provide evidence only for the toy schema. [SQLite transactions](https://sqlite.org/lang_transaction.html), [PRAGMA user_version](https://sqlite.org/pragma.html#pragma_user_version)

## Credentials and automatic unlock

Select a generic Credential Manager record, with `CRED_TYPE_GENERIC` and **`CRED_PERSIST_LOCAL_MACHINE`**. This persistence value means subsequent logon sessions for the same user on the same computer; it does not make the secret readable by all machine users. A record can hold at most **2,560 bytes**. Store a compact versioned device-session envelope rather than provider tokens, user passwords or an entire cookie jar. Bound serialized size before writing. Target names are case-insensitive: use a fixed application prefix and lower-case opaque or hashed instance/account identifiers, never case-sensitive concatenated URLs/emails. [CREDENTIALW](https://learn.microsoft.com/en-us/windows/win32/api/wincred/ns-wincred-credentialw)

Use the current Windows logon session and direct Rust calls; no application password, hardcoded Stronghold secret, or extra unlock screen is introduced. `CredWriteW` associates the record with the current token's logon session; `CredReadW` obtains that user's named record and reports missing credentials or unavailable logon sessions distinctly. Copy the required bytes in Rust and release the native allocation with `CredFree`. [CredWriteW](https://learn.microsoft.com/en-us/windows/win32/api/wincred/nf-wincred-credwritew), [CredReadW](https://learn.microsoft.com/en-us/windows/win32/api/wincred/nf-wincred-credreadw), [Microsoft Rust bindings](https://docs.rs/windows-sys/latest/windows_sys/Win32/Security/Credentials/fn.CredReadW.html)

The harness measured persistence across a fresh process in the current login, not a Windows logout/reboot. A reboot/logon test on a disposable Windows test machine remains necessary. Credential Manager is user isolation, not isolation from every other program under the same user: our second process could read the generated secret. Rust confinement here means the application never serializes secrets to its renderer, events, logs, errors, local database or browser storage.

Proposed failure and renewal contract, implementing the accepted account behavior:

- A missing, unavailable, malformed, oversized or mismatched credential stops authenticated sync and requests reauthentication. Retain the prompt database and pending work for offline use. Parse a bounded versioned envelope and verify instance/account identifiers before using it. Treat an ordinary authorization failure as authentication-required, never proof that the account was deleted.
- Rust owns credential lookup, outgoing authorization, session validation and renewal. Serialize renewal per device session; parallel windows must not race credential replacement. Accept only the selected instance's authenticated response and validate its account/session binding. Persist a replacement successfully before declaring the session durably renewed.
- A server renewal and local credential write are not one atomic transaction. Issue 10 must specify the server replay/grace behavior or accept reauthentication after a crash/storage error in that gap; either way local edits survive. A generated-secret replacement test does not validate real token renewal.
- Sign-out/switch follows the settled pending-work safeguards. Delete the exact credential record, report deletion failures, cancel requests, clear in-memory authorization and close the old partition before activating another. A late response must be checked against the session/partition generation and discarded if stale. Trustworthy whole-account deletion follows its separately specified protocol.

## Restricted renderer-to-Rust HTTP boundary

Expose typed operations such as `save_prompt`, `search_prompts`, `copy_prompt`, `sync_status` and `start_sign_in`, not raw SQL, credential retrieval or an arbitrary authenticated fetch proxy. Rust resolves the active partition and fixed REST endpoint, validates payloads and quotas, uses the configured HTTPS origin, and attaches authorization internally. Disable redirects or revalidate every redirect before credentials can cross an origin. Return parsed domain results and redacted error codes rather than raw auth headers/cookies. Instance switching must update the Rust-owned allowlist through its explicit account flow; ordinary content commands cannot supply a URL, token, file path or account authority. These are design requirements, not runtime-tested guarantees.

**Tauri's default requires care:** custom commands registered with `invoke_handler` are available to all app windows/webviews unless restricted through `AppManifest::commands` and permissions. List the protected custom commands in the build manifest, grant explicit window-specific capabilities, and validate the caller and active partition in Rust. The launcher needs search/copy/status, not arbitrary account or mutation access. Leave remote native access disabled, prevent untrusted window creation, and test denial as well as allowed calls. An empty permissions array alone does not prove future custom commands are inaccessible. [Tauri capabilities](https://v2.tauri.app/security/capabilities/)

## Reproducible measured evidence

The isolated [harness](../../research/native-persistence/src/main.rs), [manifest](../../research/native-persistence/Cargo.toml) and [lockfile](../../research/native-persistence/Cargo.lock) are research assets only. They are not linked into desktop or shared packages. Run from `research/native-persistence` with `cargo run --locked`; this is native Rust tooling, with no JavaScript runtime requirement. MSVC C build tools are required by bundled SQLite. No user credentials or production databases are read. Each run creates unique generated-data fixtures under ignored `run-data/` and two uniquely named generic credentials; both records are deleted and absence is asserted. The harness never enumerates credentials and does not print their generated contents.

Environment measured: Rust 1.94.0, Cargo 1.94.0, `x86_64-pc-windows-msvc`, Windows build 26200 / display version 25H2; no second Windows profile, reboot or physical disk exhaustion was used. `cargo fmt` could not run because this host lacks the cargo-fmt/rustfmt component; this does not affect execution results.

| Check | Observed result | Scope limit |
| --- | --- | --- |
| Failure between prompt and pending insert | Neither row retained | Injected application error |
| Successful save then reopen | Both rows retained | Connection restart |
| Concurrent connections | Reader sees committed state, second writer gets busy, retry succeeds | Two connections, not WebViews |
| Pending insert hits `SQLITE_FULL` | Prompt and pending both absent | `max_page_count` simulates SQLite full; no real full volume |
| Forced process termination after prompt / before commit | Neither row retained; integrity check ok | Parent kills only its own child |
| Forced termination after commit | Prompt and pending retained; integrity check ok | Not power loss or Windows restart |
| Failed migration then successful migration | Version/schema roll back together, then advance together; pending data retained on reopen | Toy schema |
| Forced termination during migration / after migration commit | Old/new schema version respectively; prior prompt and pending retained; integrity check ok | Toy schema |
| Credential missing/write/read/new-process read | Passed without application password prompt | Current Windows login only |
| Different instance namespace / replacement / deletion | Values separate; replacement reads correctly; both records absent after cleanup | Generated secrets only; no real renewal |

## Mandatory implementation and release validation

Under the [accepted scope decision](https://github.com/Umami-Creative-GmbH/pr0/issues/10#issuecomment-5742931074), issue 10 must retain the following mandatory implementation and release gates. A disposable Windows validation environment and the bounded native integration must provide evidence for: normal reboot/logon preserving acknowledged offline data and unattended credential access; actual disk-full/I/O-failure paths including commit/checkpoint; installed upgrade and failed migration recovery preserving pending work; a second Windows user and effective ACL checks in the real application data directory; and a Tauri two-window harness proving command permissions, renderer token non-exposure, origin/redirect restrictions, corrupt credential handling and renewal/storage-failure races. The current scaffold has none of those production boundaries implemented. Do not interrupt this user's Windows session or fill the host disk to manufacture evidence.

These remaining tests distinguish release guarantees from working library primitives. The exact synchronization payload, local revision handling, credential envelope/session renewal and account-deletion protocol remain owned by issue 10 and related auth research.
