# Better Auth access for pr0

Research for [Verify Better Auth social login across web, Windows desktop, and self-hosted deployments](https://github.com/Umami-Creative-GmbH/pr0/issues/2), under [pr0 MVP — product and technical specification](https://github.com/Umami-Creative-GmbH/pr0/issues/1). Checked 2026-09-19. This is research, not an implementation or an accepted architecture decision.

## Result and evidence boundary

Better Auth can serve the existing Next.js REST backend and social signup. There is an official desktop integration, but it targets **Electron**, not Tauri. Its client imports Electron and uses Electron application, storage, window and IPC APIs. The official documentation and repository tree inspected contain no official Tauri integration. This is a bounded finding about the inspected sources, not proof that no external integration exists. [Next.js integration](https://better-auth.com/docs/integrations/next), [Electron integration](https://better-auth.com/docs/integrations/electron), [client source](https://github.com/better-auth/better-auth/blob/41b7dc15de41a8726422c392a4857d8764828891/packages/electron/src/client.ts), [inspected source tree](https://github.com/better-auth/better-auth/tree/41b7dc15de41a8726422c392a4857d8764828891).

Latest release metadata reported [v1.7.5, published 2026-09-14](https://github.com/better-auth/better-auth/releases/tag/v1.7.5); source inspection used main commit `41b7dc15de41a8726422c392a4857d8764828891`. Live documentation can move independently of releases. Pin and verify the selected package versions before implementation. No application was built, no live provider credentials were used, and no Windows login or database compatibility test was performed.

The user-supplied [Better Auth MCP endpoint](https://mcp.better-auth.com/mcp) was also queried read-only: initialization, tool discovery, documentation search and full Electron/device-authorization retrieval succeeded. No Better Auth dependency was present in the repository manifests/lockfile, so searches used the latest documentation. MCP retrieval corroborated the browser/source findings; no persistent MCP configuration was changed.

The strongest documented Tauri-compatible building blocks are Better Auth's first-party device authorization and bearer-session plugins. A seamless browser-to-desktop handoff is also possible in principle, but the Tauri bridge must be designed and validated. Neither path requires replacing Tauri or putting Bun in the desktop runtime.

## Web login and provider configuration

Better Auth documents mounting GET/POST handlers through `toNextJsHandler` at `/api/auth/[...all]` and calling `signIn.social` from its client. pr0 can keep authentication in `apps/web` and expose authenticated application REST routes to both clients. Server Component reads alone cannot refresh browser cookies; Route Handler responses must preserve authentication headers. Use real session validation for each protected endpoint, not merely the presence of a cookie. [Next.js integration](https://better-auth.com/docs/integrations/next), [basic usage](https://better-auth.com/docs/basic-usage).

The provider's OAuth redirect and the app's post-login destination are separate. For example, the documented Google web-client callback is `https://<instance>/api/auth/callback/google`; GitHub uses the corresponding `/github` route. Provider client secrets belong only on the server. These are examples establishing feasibility, **not a provider selection**. [Google setup](https://better-auth.com/docs/authentication/google), [GitHub setup](https://better-auth.com/docs/authentication/github).

Each self-hosted deployment needs its own explicit public Better Auth base URL, secret and correctly registered provider callback URLs. Independent provider applications/credentials are the straightforward proposed operating model; a shared credential broker is not established by this research. Docker Compose cannot eliminate provider-console setup. Google documents a web application client with registered redirects. Its production OAuth policy also requires a public homepage and associated policy links, and restricts the domains an operator may register. [Better Auth options](https://better-auth.com/docs/reference/options), [Google setup](https://better-auth.com/docs/authentication/google), [Google OAuth policy](https://developers.google.com/identity/protocols/oauth2/policies).

A source discrepancy matters: Better Auth's GitHub page still says OAuth apps do not issue refresh tokens. GitHub's own current documentation and August 2026 changelog describe expiring tokens, refresh support and up to ten callback URLs. Follow provider-owned documentation and test the selected Better Auth version rather than assuming the older limitation. pr0's session token and the upstream provider token are separate credentials. [GitHub registration](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/creating-an-oauth-app), [GitHub change announcement](https://github.blog/changelog/2026-08-14-multiple-redirect-uris-and-token-refresh-for-oauth-apps/), [conflicting Better Auth page](https://better-auth.com/docs/authentication/github).

## Windows login paths

Provider authentication should occur in the system browser. Native OAuth best practice specifies an external user agent and PKCE for public native authorization-code clients; private schemes and loopback callbacks are available with different tradeoffs. Google explicitly prohibits developer-controlled embedded user agents. Do not embed a social login page in the Tauri WebView and assume it behaves like a normal browser. [RFC 8252](https://www.rfc-editor.org/rfc/rfc8252), [Google OAuth policy](https://developers.google.com/identity/protocols/oauth2/policies).

| Compatible path | What documentation establishes | Additional pr0 work / tradeoff |
| --- | --- | --- |
| First-party device authorization plus bearer sessions | Better Auth issues device/user codes; a signed-in browser user approves; native polling returns a Better Auth session token. | Build the browser approval screen and native polling/storage bridge. Extra explicit approval/code match; no required browser callback into Tauri. |
| Browser sign-in plus a PKCE-bound desktop handoff | Better Auth's Electron integration demonstrates authorization-code exchange with state/PKCE; Tauri supports deep links. | Electron's client cannot be imported as a Tauri client. Adapting its protocol or implementing a separate bridge needs a versioned contract, security review and Windows validation. |

[Device authorization](https://better-auth.com/docs/plugins/device-authorization), [Electron integration](https://better-auth.com/docs/integrations/electron), [Tauri deep linking](https://v2.tauri.app/plugin/deep-linking/).

**Device flow details:** the first-party `/device/token` response calls its value `access_token`, but it is a Better Auth session token, not a general OAuth access token. Add the bearer plugin for API use. Follow the returned polling interval and handle pending, slowdown, denial and expiry. Production requires HTTPS. The approval UI must identify the client and require explicit approval/denial and code entry or confirmation; auto-approving a URL would remove a documented protection. No OAuth Provider/JWT plugin is required for this first-party path. A separate registered-client OAuth flow exists but adds scope/resource/token infrastructure beyond the minimal same-application use case. [Device authorization](https://better-auth.com/docs/plugins/device-authorization).

**Handoff details:** Tauri's deep-link plugin supports custom schemes. On Windows an invocation starts a process with URL arguments; forwarding into the running app requires the single-instance plugin's deep-link integration. Handle initial and already-running invocation and validate the complete expected URL. A URL argument can be forged; it does not authenticate the caller. [Tauri guide](https://v2.tauri.app/plugin/deep-linking/), [Tauri JavaScript reference](https://v2.tauri.app/reference/javascript/deep-link/).

Proposed handoff contract, if selected: keep provider callbacks on the HTTPS server; send only a short-lived, single-use authorization code to the desktop; bind its redemption to the initiating native request with a verifier/state, target instance and exact callback; exchange over HTTPS. Never put the session token in a deep link. A loopback listener is an alternative, with lifecycle and listener validation work. This is a design inference from native OAuth guidance, not a supplied Better Auth Tauri recipe. [RFC 8252](https://www.rfc-editor.org/rfc/rfc8252).

Better Auth's one-time-token plugin alone is insufficient evidence of a complete native handoff. Its documented generation binds a three-minute token to the **current session**, and verification returns that session. Its public contract does not establish PKCE binding or a separate per-desktop session. Those properties must be deliberately added or proved, especially if web and desktop sign-out should be independent. [One-time-token plugin](https://better-auth.com/docs/plugins/one-time-token).

## Sessions, isolation and offline boundaries

Better Auth's normal stateful sessions have an opaque token and database expiry. Defaults are seven-day expiry with renewal after one day of use; both are configurable. Signing out ends the session, and APIs can list/revoke individual, other or all sessions. Cookie caching can delay recognition of revocation until its cache expires. Proposed starting point: database-backed sessions without cookie caching until the required revocation behavior is settled. [Session management](https://better-auth.com/docs/concepts/session-management).

The bearer plugin maps an Authorization bearer credential into Better Auth session handling and exposes a session credential through `set-auth-token` when appropriate. It is not a new provider access token or a reason to add JWTs. Its default accepts raw session tokens; enabling `requireSignature` changes that contract and must be reconciled with issuance. Protected REST routes still call session validation and apply ownership checks. [Bearer documentation](https://better-auth.com/docs/plugins/bearer), [inspected bearer implementation](https://github.com/better-auth/better-auth/blob/41b7dc15de41a8726422c392a4857d8764828891/packages/better-auth/src/plugins/bearer/index.ts).

**Proposed credential boundary:** keep desktop session tokens in native-managed, protected storage and perform authenticated HTTP through a constrained Rust bridge; expose results and identity state to UI code rather than credentials. This is a transport option: preserve the shared API contracts, api-client validation and TanStack Query responsibilities, for example through a native transport adapter; it must not silently replace those established boundaries. Tauri Stronghold provides encrypted storage but requires an unlock secret; installing it does not answer how social-login users unlock automatically. Select and test Windows storage separately. The official Electron integration likewise keeps secrets out of renderer code, but its storage implementation is Electron-specific. [Tauri Stronghold](https://v2.tauri.app/plugin/stronghold/), [Electron integration](https://better-auth.com/docs/integrations/electron).

**Product inference:** offline browsing/copy/create/edit is local library behavior, not proof of a currently valid server session. A disconnected desktop cannot renew or learn about revocation. On reconnect, validate before upload; expired/revoked credentials require reauthentication. Pending changes must remain associated with `(instance, user)` and must never upload into a different account. Decide whether offline access continues after session expiry, what sign-out removes, and whether queued edits are retained/exported. Better Auth does not specify these pr0 product rules. Session expiry and refresh facts above establish the boundary. [Session management](https://better-auth.com/docs/concepts/session-management).

Account linking is enabled by default subject to verification rules; explicit configuration is needed to match pr0's chosen identity policy. Linking, account recovery, fallback login and provider selection remain human decisions. Do not let framework defaults silently decide whether two sign-in buttons reach the same library. [Users and accounts](https://better-auth.com/docs/concepts/users-accounts).

## Cookies, origins and deployment

Better Auth uses secure-cookie settings, origin/redirect validation and other CSRF protections. Keep those checks enabled. Its default session cookie SameSite policy is Lax; browser and native transports must be treated separately. If native requests supply Origin/Referer, they must satisfy the allowlist. Set an explicit public base URL and narrowly enumerated trusted origins; do not globally disable checks to accommodate Tauri. [Security reference](https://better-auth.com/docs/reference/security), [options](https://better-auth.com/docs/reference/options).

Proposed deployment: serve the web frontend and REST/auth endpoints at one HTTPS origin behind the existing reverse proxy. This avoids a cross-site browser-cookie dependency. Browser CORS policy still needs explicit handling if origins are split; native HTTP is not protected by browser CORS. Origin validation is not library authorization. The repo already requires server-only credentials and REST ownership validation. Cookies and `set-auth-token` responses must survive the proxy; prevent public caching of authenticated responses. [Cookies](https://better-auth.com/docs/concepts/cookies), [bearer source](https://github.com/better-auth/better-auth/blob/41b7dc15de41a8726422c392a4857d8764828891/packages/better-auth/src/plugins/bearer/index.ts), [repository architecture](../architecture.md).

## Bun and database compatibility

| Candidate | Evidence | Boundary |
| --- | --- | --- |
| Bun SQLite | Better Auth explicitly accepts `Database` from `bun:sqlite` and documents Bun CLI execution. | Directly documented path; still requires application migration, backup and concurrency decisions. |
| PostgreSQL through Drizzle and Bun SQL | Better Auth documents its Drizzle adapter with `provider: 'pg'`; Drizzle documents `drizzle-orm/bun-sql` with a `SQL` client from Bun. | A composition of documented interfaces; not end-to-end validated by this research. |
| Better Auth's direct PostgreSQL example | Uses `pg.Pool`. | Does not meet this repo's required Bun-native PostgreSQL client policy as written. Do not copy it or assume `bun.SQL` is a drop-in replacement. |

[Better Auth SQLite](https://better-auth.com/docs/adapters/sqlite), [Better Auth Drizzle](https://better-auth.com/docs/adapters/drizzle), [Drizzle Bun SQL](https://orm.drizzle.team/docs/connect-bun-sql), [Better Auth PostgreSQL](https://better-auth.com/docs/adapters/postgresql), [repository architecture](../architecture.md).

For a selected PostgreSQL stack, use a focused compatibility investigation before implementation commitment: pin Better Auth, adapter, Drizzle and Bun versions; generate schema under Bun; apply migrations through the intended Bun-only process; prove user/account/session operations, rollback, uniqueness and concurrent one-use device/code redemption. The current Drizzle pages show release-candidate packages, and Better Auth distinguishes Relations v1/v2 adapters, so generic compatibility is not a version guarantee. Auth schema generation and database migration are separate with the Drizzle adapter. No Redis is required by the stateful database-session design; do not introduce one by default. [Drizzle adapter](https://better-auth.com/docs/adapters/drizzle), [Drizzle Bun SQL](https://orm.drizzle.team/docs/connect-bun-sql), [database concepts](https://better-auth.com/docs/concepts/database).

## Decisions and precise follow-ups

Existing map tickets should resolve these without this report choosing for the user:

1. **Account access:** which social providers, fallback/recovery method and explicit linking policy? Is device approval acceptable, or must login return seamlessly to desktop?
2. **Session/offline behavior:** session duration, independently revocable desktop sessions, offline access after expiry, sign-out data/queue handling and safe instance switching?
3. **Architecture:** SQLite or PostgreSQL? If PostgreSQL, does the pinned Drizzle/Bun SQL composition pass the compatibility investigation above without adding a disallowed driver?
4. **Windows integration:** which native credential store and unlock behavior? If handoff is chosen, which callback transport and how are state/verifier binding, wrong-instance callbacks, replay, cold start and running-instance delivery verified?
5. **Self-hosting:** operator-owned provider registrations, required HTTPS/public URL setup, enabled-provider configuration, registration controls and guidance when no social provider is configured?

Before claiming an implementation ready for release, demonstrate: provider signup/login/cancellation; separate web/desktop sessions; renewal and revocation; unknown/malformed/replayed callback or device code; offline expiry followed by reconnect; two accounts and two independent instances; and a fresh Compose deployment with its own provider credentials. These are proposed acceptance checks, not tests already run.
