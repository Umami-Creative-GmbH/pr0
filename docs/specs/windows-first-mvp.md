# Implement the pr0 Windows-first MVP

Implementation specification derived from completed decision map #1. Product decisions are approved, and the user explicitly confirmed the testing boundaries below on 2026-09-19. This document neither starts implementation nor certifies a release.

## Problem Statement

People who repeatedly use prompts need to find and reuse them faster than they can in scattered notes or text files. They need one personal library across desktop and web, organization that remains optional, and a short path from needing a prompt to having it in the clipboard. A Windows desktop must remain useful without connectivity, and reconnecting must not silently lose competing edits or mix accounts.

The repository currently supplies the Bun/Next.js/Tauri foundation, a throwaway library and launcher prototype, and isolated research harnesses. It does not yet provide the complete production account, storage, synchronization, search, native lifecycle, or deployment behavior approved in #1. The implementation must replace prototype shortcuts with the accepted contracts.

## Solution

Deliver the full approved Windows-first MVP: a free personal prompt library accessible through a web application and a Windows desktop application. Users sign in, create and organize reusable prompts, search and filter them, optionally fill typed variables, and copy with clear confirmation. The quick launcher makes search-to-copy available through the resident desktop's global shortcut and manual entry points.

Desktop saves are durable locally and synchronize automatically. Conflicting text is preserved in independent conflict copies. The interface distinguishes drafts, local saves, server acceptance, incomplete downloads, pending work, authentication requirements, and work needing attention. Self-hosters receive a portable Docker Compose deployment with documented configuration, recovery, and upgrades.

The approved resolutions and committed specifications linked in Further Notes are normative acceptance material, incorporated into this specification. This synthesis does not replace their precise algorithms, protocol traces, numeric bounds, or edge cases. Later explicit amendments identified by the approved readiness handoff take precedence over earlier proposals and prototype behavior.

## User Stories

2. As an account owner, I want a verified account email before library access, so that identity and recovery have a verified destination.
3. As a returning user, I want to recover access through my verified email and reset my password, so that losing one social login does not necessarily strand my library.

5. As an account owner, I want to verify a new email and notify my old address when it changes, so that account changes remain controlled and visible.
6. As an account owner, I want to see and revoke individual sessions or all other sessions, so that I can stop access from a particular device.
7. As a desktop user, I want to approve a matching device code in my system browser, so that the desktop receives its own session without embedded social login.

9. As a self-hosted user, I want to select my HTTPS instance before login, so that I can use my own service while keeping its account and library independent.

69. As a Windows user, I want one resident application per Windows user with tray entry points, so that repeated launches cannot create competing writers or shortcuts.

71. As a Windows user, I want opt-in startup that is off by default and starts quietly in the tray, so that pr0 follows my startup choice without unsolicited windows.
72. As a Windows user, I want the actual registered shortcut shown and manual launcher entry plus Retry registration when candidates are unavailable, so that collisions do not prevent access.
73. As a launcher user, I want focused search on activation and visible pointer and keyboard recovery when Windows refuses focus, so that the application never mistakes a shown window for typing readiness.
74. As a launcher user, I want active-only search, fresh query/filter state per opening, and dismissal after successful copying, so that the launcher stays dedicated to fast retrieval.
75. As a Windows user, I want Save and quit, Discard and quit, or Cancel for unsaved drafts while durable pending work survives ordinary quit, so that exiting does not silently discard edits or require connectivity.
76. As a keyboard or assistive-technology user, I want every core action, dialog, picker, error, and tray recovery path accessible with visible focus and usable zoom, so that I can complete the workflow without a pointer.
77. As a user with a maximum-size library, I want the agreed responsiveness and resident-resource budgets met without changing results or durability, so that pr0 remains useful as my library grows.
78. As a desktop user, I want signed installation, notified user-approved updates, and preserved local work across upgrades, so that maintaining the application does not endanger my library.
79. As a user of an older desktop or self-hosted server, I want compatibility checked before upload with an actionable update path, so that incompatible versions preserve offline work.

## Implementation Decisions

- **Scope and architecture.** Build the complete personal-library MVP approved in #1. Retain Bun as the sole JavaScript/TypeScript runtime, Next.js REST Route Handlers for the web/API, Tauri/Rust and Vite for Windows, shared UI/contracts/client, and TanStack Query for server state. Desktop does not run Next.js. Shared flows use REST rather than Server Actions. Read the installed framework guides before changing framework code. Add no Redis or replacement runtime by default.
- **Production boundaries.** Extend the web routing/API, shared contract and validated client modules; build production account, library, synchronization, search, and native service behavior behind those boundaries. Shared UI handles rendering and interaction, with platform adapters for browser and native operations. Query caches are disposable views. Reuse accepted prototype interaction direction, but replace in-memory storage, decorative sync feedback, incomplete variable handling, limited result lists, and permissive prototype native messaging.
- **Persistence and ownership.** PostgreSQL is authoritative for accounts, libraries, revisions, operations, receipts, notices, and synchronization state. Bun SQL supplies parameterized queries, pooling, and transactions; Better Auth's pinned Drizzle adapter uses the validated Bun-native PostgreSQL chain with transactions enabled. Rust owns local SQLite, credentials, authenticated HTTPS, synchronization, and clipboard authority. Rebuildable server SQLite search projections have no independent write authority.
- **Identity and schema.** Bind every entity, relationship, operation, and cache to immutable instance/account identities. Generate UUIDv4 object and operation identities; never reuse deleted identities. Serialize monotonic 64-bit library revisions as decimal strings, use server-accepted UTC dates, and establish a new recovery epoch after disaster restore. Persist the contract's serialization/quota row, entities, membership revisions, deletions, merge aliases, operation receipts, conflict notices, changes, snapshots, and authentication records with library-scoped constraints.
- **Accounts and access.** Require Better Auth, verified account email, Google/GitHub plus email/password on the hosted service, explicit provider linking, recovery, independent revocable sessions, and 30-day inactivity expiry. Sensitive actions require the specified browser-session-bound proof from the preceding ten minutes; normal renewal or desktop approval is insufficient. Protect direct auth-library routes as well as application wrappers. Desktop uses explicit system-browser device approval and a separate bearer session; browser/device provenance remains server-owned. Keep session credentials in same-user Windows Credential Manager, never renderer state. Preserve local work on credential failure, expiry, or revocation. Sign-out/switching and verified account deletion follow the approved pending-work and exact-partition cleanup rules.
- **Lifecycle.** Require nonblank title/content; trim titles/descriptions while preserving nonblank content exactly. Duplicate titles are allowed. Duplication captures the chosen source snapshot into a new active, unfavorited prompt with fresh dates, no usage, and a derived copy title. Archived prompts retain metadata and remain editable/copyable in archive only. Permanent deletion requires confirmation. Actual saved text/assignment/favorite/archive changes advance modification time; usage, unchanged saves, and referenced-name renames do not.
- **Organization.** Keep flat optional collections and multiple tags. Separate canonical organization identity from accent-insensitive search keys. Apply the approved Unicode normalization and name-collision rules; tag rename collisions require explicit merge, while collection collisions retain work for correction. Organization deletion clears assignments and preserves active/archived prompts. Implement the management dialog, complete searchable pickers, counts, affected-prompt review, and unavailable-filter behavior from #20. Merge aliases reconcile pending assignments but never silently substitute UI filters.
- **Durable desktop saves.** A single Rust storage owner commits local projection, required search state, local revision, baseline/dependency information, and outbox work atomically before reporting Saved on this device. Use verified SQLite WAL, FULL synchronous mode, foreign keys, bounded retries, and no blocking database work on the UI thread. Freeze a transmitted operation's identity/payload; subsequent edits become successor work. Apply acknowledgements, successor rebasing, and conflict-copy mappings atomically. Preserve overlays until accepted records arrive. Never hold a transaction across HTTP, clipboard access, or human input. Keep failed drafts and corrupt data available for recovery instead of clearing databases or WAL files.
- **Synchronization and conflicts.** Use the approved typed operation envelope and per-operation serialized server transactions. An identical operation UUID and canonical payload hash returns its stable receipt; changed payload under that UUID fails. Effects, quotas, revisions, notices, and receipts commit together. Reconcile independent fields; preserve full competing text in independent conflict copies, including edit/delete in both arrival orders. Preserve subsequent local edits when an earlier variant maps to a copy. Apply documented metadata ordering, tag removal causality, merge aliases, deletion precedence, and dependency handling. Quota-blocked preservation leaves server state unchanged and local work actionable; unrelated operations continue.
- **Downloads and recovery.** Use bounded HTTPS long polling with a 25-second maximum wait and durable cursor-based changes. Retain change records for 90 days and compact deduplication/deletion/alias information for the account lifetime. Expired cursors request a consistent replacement snapshot; snapshots expire after 15 minutes, carry manifests/digests, and bound pages to 4 MiB uncompressed. Stage replacements while preserving the usable baseline and pending work; advance cursors only with committed data. Reauthenticate and check deletion evidence before upload. A recovery epoch change never authorizes uploading every formerly acknowledged row.
- **Search semantics.** Implement the exact versioned Unicode 17 normalization, scalar-value title comparison and UUID tie-breakers from the contract. Match literal substrings across five fields with AND terms and filters; preserve punctuation and the six approved relevance tiers. Keep archive isolation, deterministic explicit sorts, per-view sort memory, identity-based selection, and copy-based Recents. Server and desktop agree for equivalent snapshots. No fuzzy, semantic, stemming, or query-operator behavior is introduced.
- **Search execution.** Use the approved compact per-field trigram candidates, exact substring verification, adaptive persisted one/two-code-point postings, and ordered bounded page evaluation in both server Bun workers and Rust. Candidate indexes may not change eligibility or ranking. Update desktop projection/search/outbox atomically; advance server derived indexes from committed PostgreSQL changes. Admit a query against at least its required revision or report preparation/retry. Use revision-bound summaries with default 50/maximum 100 rows per page and separate full-text reads; restart changed-result pagination while preserving selection. Never cap total logical matches. Keep the accepted cache/worker budgets and staged rebuild behavior.
- **Shared API.** Implement the contract's versioned capabilities, prompt search/detail, organization, conflicts, mutations, receipt lookup, changes, snapshots, sessions/revocation, browser reauthentication, and deletion-receipt families. Keep validators, OpenAPI, request/response encoding, stable error codes, and implementations consistent. Enforce authentication, ownership, quotas, decoded-body bounds, cancellation, and explicit per-operation outcomes; do not label a mixed batch fully synchronized. Web uses secure HttpOnly cookies and CSRF/origin protection. Rust sends bearer credentials only to its validated selected HTTPS origin, revalidates redirects, and rejects stale partition responses. Typed least-privilege native commands replace generic authenticated fetch or arbitrary message forwarding.
- **Copy and recency.** One common application-managed clipboard boundary allows one write at a time, including across desktop windows. Validate current identity, eligibility, template state, and bounded output before beginning. Freeze output during a write; do not queue a later implicit write. Success creates the existing UUID usage operation with occurrence time; failure creates no use. Separate usage-storage failure from clipboard success and retry only usage. Recents contains distinct active used prompts without an arbitrary expiry or count cap. Accepted occurrence times use the contract's future-time correction and maximum rule; retries, delayed delivery, or deletion cannot manufacture a new prompt or later use.
- **Variables.** Implement #21's exact saved-content grammar, malformed-candidate scan, immediate-backslash escaping, first-appearance order, case-sensitive names, repeated-name aggregation, and one-pass literal substitution. Optional lowercase string/number annotations do not make values optional; any recognized numeric occurrence imposes lexical decimal validation for that name. Preserve valid input exactly without floating-point coercion. Bound each value and total output at 256 KiB UTF-8; reject NUL, malformed Unicode, blank values, and oversized output without truncation. Values and output stay transient and excluded from persistence, sync, URLs, logs, telemetry, receipts, and application crash attachments. No new variable-value records or mutation kinds are needed. Apply the canonical back/cancel, template-change restart, deletion/archive, blur, in-flight-write, and account-transition rules.
- **Status and review.** Keep explicit Save and distinguish unsaved draft, local durable save, and server acknowledgement. Desktop may close after local commit; web waits for server acknowledgement and guarantees failed-draft retention only in the open tab. Implement one compact status control with coexisting details, last completed check, persistent attention entries, and nonblocking conflict review. Keep both / Mark reviewed acknowledges a notice without deleting text or a copy. Background synchronization never steals focus or blocks copying available prompts.
- **Windows lifecycle.** One resident process per Windows user owns data, tray, and shortcut. Closing hides and retains draft state; Quit ends residency after the approved unsaved-draft choices, while durable pending work survives without waiting for network acknowledgement. Startup is opt-in and quiet. Try Ctrl+Shift+P, Alt+Space, Ctrl+Alt+P, and Ctrl+Shift+Space in order; show the actual result and support explicit retry/manual entry. Observe actual foreground focus; initial refusal leaves the launcher visible with Click to search plus keyboard recovery, and blur dismissal begins only after focus acquisition. No separate helper starts a fully quit app on a shortcut.
- **Limits and response bounds.** Enforce 10,000 prompts including archive, 100 MiB total library text, 256 KiB content, 200-code-point titles and queries, 2,000-code-point descriptions, 60-code-point organization names, 1,000 tags, 200 collections, and 20 tags per prompt. Include retained conflict-title text in storage accounting. Warn at 90%; archiving frees no capacity. Allow permitted deletions/usage-reducing changes. Bound mutation requests by 100 operations and 4 MiB decoded JSON, with bulk organization operations as singletons. Preserve rejected work with precise errors and retry delays.
- **Deployment and operations.** Extend portable Compose as consuming features arrive with canonical PostgreSQL storage, persisted derived search, one-shot Bun migrations, readiness gates, secret-file support, and persistent identity/keys. Keep database and search ports private. Runtime origin, trusted ingress, SMTP, optional OAuth, registration modes, and bounded admission follow #11. Self-hosting defaults to closed signup with explicit first-account admission; the hosted service offers public signup. Keep the accepted request/email/work limits, operator suspension and registration controls, health, redacted logs, storage alerts, and recovery commands. Operators choose suitable hosts, domains, TLS, email and backup integrations; no vendor or server purchase is required by this spec.
- **Deletion-safe restore.** Implement the contract's immutable trust anchor, signed key continuity, minimal indefinitely verifiable Ed25519 deletion receipts, and independent durable deletion ledger. Coordinate deletion intent, live purge, and completion publication with zero loss of acknowledged account deletions. Ordinary outages, missing receipts, and generic authorization errors never authorize local deletion. Restore stays closed until complete evidence is replayed, deleted data is absent, restored sessions/action tokens are invalidated, a new epoch exists, and readiness passes. Ordinary encrypted off-server backups retain at most 30 days and meet one-hour loss/24-hour recovery objectives; rehearse before release and quarterly.
- **Distribution and support.** Ship a signed per-user Windows installer and separately verified, user-approved updates. Official update trust remains independent of the selected data instance. Preserve local data/outboxes through supported migrations; refuse unknown newer schemas safely. Support current desktop and releases from the preceding 90 days. Target supported Windows 11 x64/current WebView2 and current/previous major desktop Chrome, Edge, Firefox, and Safari. Mobile web stays usable; dedicated mobile acceptance is deferred. Target WCAG 2.2 AA and preserve the manual accessibility checks.

## Testing Decisions

The user confirmed the following testing boundaries on 2026-09-19: the public REST API for server behavior and typed native commands for desktop behavior, supplemented by shared conformance fixtures, UI journeys, and installed Windows checks. They implement the approved acceptance obligations without adding product scope.

- **One behavioral scenario set, two necessary system boundaries.** Use the existing public REST request/response boundary as the main server integration seam. Use the existing Tauri command boundary, narrowed to production typed commands, for native offline, restart, credential, clipboard, and partition behavior that a server request cannot prove. Share scenario inputs and expected public outcomes where applicable. Do not add separate test-only facades for each module or force native behavior through a generic REST proxy.
- **Server integration.** Exercise account/session guards, library lifecycle and organization, search, quotas, receipts, reconciliation, snapshots, and deletion through public requests against isolated real PostgreSQL and SQLite projections. Assert returned data, error codes, visibility across accounts/devices, and state read back through public operations. Use the existing route tests' Request/Response pattern and the Better Auth harness's HTTP-handler tests as prior art, extending coverage to the actual served Next.js/Bun stack where cookies, origin checks, routing, and direct-route bypass matter.
- **Native integration.** Drive typed native operations against temporary account partitions and controlled service responses, then reopen the process and observe saved prompts, pending status, receipts, and search. The existing native persistence harness provides prior art for generated SQLite fixtures, own-child termination, credential round trips, and interrupted migrations. Promote its useful scenarios into production integration coverage without treating the throwaway harness as production code or complete Windows evidence.
- **Focused shared-contract conformance.** Extend the prior normalization, retrieval, lifecycle, variable, copy, and view-state examples as public-input/output fixtures for production behavior. Run identical Unicode, ranking, paging, parser, lexical-number, and output-bound vectors in TypeScript and Rust. Test observable ordering, exact text, errors, and final state rather than private helper structure, SQL layout, component internals, or callback counts unrelated to contractual effects. Prototype behavior that contradicts an approved amendment must not become an expected result.
- **Validated client coverage.** Extend existing client tests for invalid success payloads, typed HTTP failures, cancellation, retry classification, and origin cache isolation to account/instance/epoch/revision partitioning and new API methods. Verify that stale responses and switched-account operations cannot update the active library.
- **Controlled failures at external effects.** Introduce deterministic failure controls only where real effects require them: transport interruption or lost response, clipboard rejection/delayed completion, storage failure/process termination, clock input, email/provider responses, and independent deletion-ledger availability. Keep storage and reconciliation real in durability tests. Observe recovery through the same public boundaries, without exposing every implementation step as a public test API.
- **Cross-device acceptance.** Cover all fourteen contract validation groups and linked canonical examples, including same/different-field edits, successors during uncertain delivery, text/delete in both orders, quota-refused preservation, tag merge/deletion races, interrupted and expired snapshots, more-than-90-day absence, account/instance switches, same-email recreation, stale receipts, server restore, and real authentication bypass attempts. Repeated delivery must have one effect and may never erase a later local variant.
- **UI journeys.** Add browser and desktop interaction coverage for login, list/detail/editor, complete result/picker access, empty states, unavailable filters, organization confirmation/review, honest save/sync states, conflict review, variable entry/restart/cancel, and copy failure/success. Drive accessible controls and verify visible outcomes/focus; avoid rendering snapshots as substitutes for behavior. Existing UI is intentionally untested prototype prior art, so this production journey coverage is new.
- **Installed Windows and accessibility gates.** Exercise the signed installed build for tray overflow keyboard access, startup registration/failure/external disablement, single-instance races, each/all shortcut collisions, focus refusal, elevated/secure-surface recovery, sleep/resume, mixed DPI/monitor removal, draft-aware quit, native command denial, credentials and second-Windows-user isolation, and updates with pending work. Perform the required keyboard, zoom, and manual screen-reader journeys. Record actual Windows, WebView2, browser, application, and hardware versions; prior human prototype acceptance does not supply missing measurements.
- **Performance and operations gates.** Execute the exact accepted maximum-library and aggregate-server workloads below, including end-to-end debounce/render time, cold persisted indexes, concurrent organization/search work, and body/value bounds. Rehearse full-feature self-hosting, migration failure, encrypted backup recovery, unavailable/incomplete deletion evidence, key continuity, and signed update verification. Starter-container success and isolated benchmarks are supporting evidence only.

| Backup and restore | At most one hour ordinary data loss; restore within 24 hours; ordinary copies expire within 30 days; zero loss of acknowledged deletion evidence; successful pre-release and quarterly rehearsals. |

Known data loss, account-isolation failures, broken core keyboard flows, failed restore/update checks, or failure of the accepted capacity/performance workloads block release. Passing existing foundation/prototype tests does not establish these production behaviors. This drafting task adds no implementation tests or runtime changes.

## Out of Scope

- Team accounts, organizations, shared libraries/prompts, collaboration permissions, and federation or cross-instance library migration.
- Visible prompt version history, advanced usage analytics, automatic text-merge editors, and a trash/undelete promise for permanently deleted prompts.
- macOS/Linux desktop, Windows 10, native Windows ARM64, and dedicated mobile acceptance for the first release.
- Guest libraries, multiple simultaneously retained signed-in desktop libraries, and guaranteed offline browser reload or draft recovery after closing the tab.
- Persisted or synchronized variable values, expression evaluation, nested substitution, defaults, optional values, and type annotations beyond string/number.
- Semantic/fuzzy search, stemming, special query syntax, nested collections, collection merge, bulk-selection cleanup, and a custom shortcut editor.
- An independent helper/service that launches a fully quit desktop through the shortcut, application-level encryption of prompt SQLite, and promises of unsaved-draft survival after forced termination or disk loss.
- Selecting a mandatory host, domain, proxy, SMTP vendor, backup vendor, signing vendor, or monitoring stack. Actual provisioning and production rollout are separate operational work; their application support and release acceptance remain in scope.
- Replacing the approved Bun/Next.js/Tauri foundation or Better Auth, or treating this specification task as authorization to implement or deploy the MVP now.
